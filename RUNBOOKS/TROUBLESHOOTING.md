# Troubleshooting Runbooks

This document records infrastructure troubleshooting patterns and lessons from the homelab.

Examples are intentionally sanitised. Real addresses, hostnames, interface names, device identifiers, container IDs, credentials, and forwarding mappings are not published.

## Case 1 — Service Exposure Architecture

The lab initially relied too heavily on router-specific service exposure and DNS behaviour.

The architecture was separated into:

| Layer | Responsibility |
|---|---|
| Router/LAN | Upstream connectivity |
| Proxmox | Routing, NAT, selective DNAT |
| Nginx | HTTPS and reverse proxy |
| Application | Authentication and application logic |
| Storage | Persistent data |

Live mappings are deliberately excluded.

## Case 2 — Remote Access and TLS Trust

The lab evolved from LAN-only private-CA access to an authenticated overlay network combined with publicly trusted HTTPS.

The responsibilities are separated:

~~~text
Remote client
     |
     | authenticated overlay network
     v
Nginx
     |
     | HTTPS / TLS termination
     v
Internal application
~~~

The overlay network controls who can reach the private ingress point. TLS provides application-layer confidentiality and standard client trust.

The public repository documents this architecture without publishing the real domain, overlay addresses, DNS records, certificates, or credentials.

## Case 2A — DNS Validation for Public TLS

A wildcard certificate can be issued without exposing the private service network by using DNS-01 validation.

Operational flow:

1. Request certificate for the public service namespace.
2. ACME server provides a DNS challenge.
3. DNS challenge is published through the DNS provider's API.
4. Certificate authority validates the DNS record.
5. Certificate is issued to the reverse proxy.
6. Nginx is reloaded after a successful renewal.

DNS API credentials must remain outside Git and should be stored with restrictive permissions. Certificate private keys must also remain outside the repository.

For troubleshooting, verify the challenge publication, certificate validity, renewal configuration, and reverse-proxy reload independently.

## Case 3 — File Browser Quantum Deployment

A web-based file manager needed access to an existing data volume while remaining isolated from the physical disk and direct LAN application exposure.

The physical filesystem is mounted by the Proxmox host. A directory from that host mount is presented to the application container through an LXC mount point.

~~~text
Physical volume
     |
     v
Proxmox host mount
     |
     v
LXC mount point
     |
     v
File Browser Quantum
~~~

File Browser uses the mounted directory as its source and is managed by systemd.

Validate in this order:

1. Confirm the host filesystem is mounted.
2. Confirm the LXC receives the mount.
3. Confirm expected files are visible inside the container.
4. Start File Browser.
5. Confirm the application responds locally.
6. Test connectivity from the reverse-proxy container.
7. Test through Nginx.
8. Test through the client hostname.

## Case 4 — Relative Application Database Path

The File Browser configuration generated by interactive setup used a relative SQLite database path.

A relative path can resolve differently depending on the process working directory.

The systemd unit explicitly defines the application's working directory so the relative database location is deterministic.

Validate that the service remains active across restarts and that it retains configuration and authentication state.

## Case 5 — Reverse Proxy Backend Connectivity

There are multiple independent connectivity layers:

~~~text
Client
  ↓
Proxmox
  ↓
Nginx
  ↓
File Browser
  ↓
Storage
~~~

Testing only the client-facing URL cannot identify which layer failed.

Test the backend from inside the Nginx environment first, then test the full HTTPS path.

## Case 6 — HEAD vs GET False Negative

A direct HTTP HEAD request returned 404 while a normal GET request returned a successful response.

The root cause was different application handling for HEAD and GET.

Use a request that matches the real browser workflow when validating application availability.

~~~text
GET /
~~~

A health check should validate the status code and response body rather than assuming HEAD and GET are equivalent.

> A test is only meaningful when it reproduces the protocol behaviour of the client being diagnosed.

## Case 7 — Large File Uploads Through a Reverse Proxy

Large uploads through a reverse proxy can fail even when the backend works correctly when accessed directly.

Inspect:

- request-body limits
- proxy timeouts
- buffering
- connection reuse
- headers
- upstream availability

Avoid blindly disabling limits in production. Select limits based on workload and abuse risk.

## Troubleshooting Methodology

Work from the bottom of the stack upward.

### Network

~~~text
ip addr
ip link
ip route
~~~

Verify interface state and routes locally without documenting live addresses.

### Forwarding and NAT

~~~text
cat /proc/sys/net/ipv4/ip_forward
iptables -t nat -L -n -v
iptables -L FORWARD -n -v
~~~

Do not paste live firewall rules into a public repository.

### Listening services

~~~text
ss -lntp
~~~

Redact live addresses and service mappings before committing output.

### Nginx

~~~text
nginx -t
~~~

Inspect listeners, server names, TLS settings, proxy targets, request-body limits, and timeouts.

### TLS

~~~text
openssl s_client -connect <SERVICE>:<TLS_PORT> -showcerts
~~~

Redact certificate identities and private information before documenting output.

### Backend

~~~text
curl http://<BACKEND>/
~~~

This separates application failures from Nginx, TLS, NAT, and client failures.

## Security Redaction Checklist

Before committing troubleshooting output:

- [ ] No real IP addresses
- [ ] No real hostnames
- [ ] No public IP addresses
- [ ] No MAC addresses
- [ ] No Wi-Fi names or credentials
- [ ] No passwords or hashes
- [ ] No API keys or tokens
- [ ] No private CA keys
- [ ] No server private keys
- [ ] No exact DNAT/port mappings
- [ ] No physical disk identifiers
- [ ] No container IDs
- [ ] No unredacted certificates
- [ ] No application databases or backups

> Troubleshoot from the network boundary toward the application, isolate each layer, make the smallest required change, validate the result, and document the engineering lesson without publishing the live environment.

## Case 8 — Overlay DNS and Split-DNS Behaviour

Private service names can resolve differently for approved overlay-network clients than they do through ordinary public DNS.

The intended model is:

~~~text
Public DNS
  |
  +--> public-facing records only

Overlay DNS
  |
  +--> private service records
  |
  +--> overlay-network addresses
~~~

When troubleshooting, distinguish between:

- the DNS server queried directly by a diagnostic command
- the resolver selected by the operating system
- the resolver used by the application
- public DNS versus private overlay DNS

A successful application request can therefore coexist with an empty result from a diagnostic tool that queried a different resolver.

Never publish the real private DNS zone, overlay addresses, or device identifiers in troubleshooting output.
